# Бінарний контейнер Taruck v1 — специфікація байтів

Статус: зафіксована специфікація для реалізації A4 від 6 жовтня 2026 року. Усі цілі числа записуються в порядку little-endian. Документ описує байти у файлі; назви полів нижче наведені для пояснення й не записуються у файл. Усередині контейнера немає JSON або BinaryFormatter.

## Заголовок і типи файлів

Заголовок має фіксовану довжину **29 байтів**: сигнатура ASCII `TARUCKPK` (8 байтів), `containerVersion` UInt16 (значення 1), `fileType` Byte (1 — LocalData, 2 — FullSaveExport, 3 — CharacterExport, 4 — ItemExport), `flags` UInt16 (у v1 має дорівнювати нулю), `payloadLength` UInt64, `payloadCrc32` UInt32 та `mediaEntryCount` UInt32. Читач відхиляє непідтримувану версію контейнера, невідомий тип, прапорці, надмірну довжину, обрізаний файл і зайві байти наприкінці. Новішу невідому версію не можна тлумачити як v1.

Для основних даних використовується CRC-32/ISO-HDLC: віддзеркалений поліном `0xEDB88320`, початкове значення й фінальний XOR — `0xFFFFFFFF`. CRC охоплює лише байти основних даних. Контрольний вектор: UTF-8 `123456789` дає `0xCBF43926`.

## Записи TLV і типи значень

Основні дані та кожен вкладений об’єкт складаються з послідовних записів TLV: `fieldId` UInt32, `valueType` Byte, `valueLength` UInt32, потім рівно `valueLength` байтів значення. Відоме поле має траплятися один раз і мати визначений нижче тип. Невідомі `fieldId` дозволено пропускати лише в межах підтримуваної версії схеми. Повтор відомого поля або неправильний тип є помилкою. Обов’язкові поля мають бути присутніми. Довжина основних даних задає кінець верхнього об’єкта, а довжина вкладеного об’єкта — його власний кінець.

| valueType | Назва | Байти значення |
|---:|---|---|
| 1 | Utf8 | Байти UTF-8 без завершального NUL; декодування з перевіркою помилок |
| 2 | Int32 | Знакове ціле, 4 байти |
| 3 | UInt32 | Беззнакове ціле, 4 байти |
| 4 | Float32 | IEEE-754 binary32, 4 байти; NaN і нескінченність заборонені |
| 5 | Boolean | Один байт: 0 або 1 |
| 6 | Object | Вкладені записи TLV |
| 7 | Collection | Кількість елементів UInt32, далі для кожного елемента довжина UInt32 і байти елемента; тип елемента визначається його `fieldId` |
| 8 | Bytes | Довільні байти; зарезервовано, у моделі v1 не використовується |

Колекції не містять `null`-елементів. Порожній рядок має нуль байтів; під час запису `null`-значення рядка моделі перетворюється на порожній рядок. Порядок елементів списку зберігається. Елемент-об’єкт містить повні вкладені записи TLV. Примітивний елемент містить лише байти свого значення, без внутрішнього заголовка TLV. Порожня колекція — це чотири нульові байти.

## Реєстр fieldId

Основні дані кожного файлу обов’язково містять: `1 schemaVersion` Int32 = 1; `2 appVersion` Utf8 — непорожню версію застосунку, який записав файл; `3 rulesVersion` Utf8 = `DND5E`; і один кореневий об’єкт із ID 10. Для файлів персонажа й предмета корінь має тип Object; для повної колекції та локального сховища це також Object із полями AppSaveData. Невідповідність `fileType` є помилкою, навіть якщо структуру кореня вдалося б прочитати.

| Об’єкт | ID полів і типи |
|---|---|
| AppSaveData | 1 lastActiveCharacterId Utf8; 2 characters Collection<CharacterData> |
| CharacterData | 1 id Utf8; 2 characterName Utf8; 3 maxHealth Int32; 4 currentHealth Int32; 5 inputData Collection<Utf8>; 6 toggleData Collection<Boolean>; 7 sliderData Collection<Float32>; 8 dropdownData Collection<Int32>; 9 sceneStates Collection<CharacterSceneData>; 10 sharedStringData Collection<StringSaveEntry> |
| CharacterSceneData | 1 sceneName Utf8; 2 inputData Collection<Utf8>; 3 toggleData Collection<Boolean>; 4 sliderData Collection<Float32>; 5 dropdownData Collection<Int32>; 6 stringData Collection<StringSaveEntry>; 7 intData Collection<IntSaveEntry>; 8 floatData Collection<FloatSaveEntry>; 9 stableFieldVersion Int32 |
| StringSaveEntry | 1 key Utf8; 2 value Utf8 |
| IntSaveEntry | 1 key Utf8; 2 value Int32 |
| FloatSaveEntry | 1 key Utf8; 2 value Float32 |
| InventoryItemExportData | 1 itemName Utf8; 2 itemDescription Utf8; 3 category Int32; 4 weaponIndex Int32; 5 armorIndex Int32; 6 bagsIndex Int32; 7 magicIndex Int32; 8 otherIndex Int32; 9 chegerIndex Int32; 10 imageMediaId UInt32 — необов’язкове поле, відсутнє без зображення |

Зображення предмета записується як медіазапис. Значення `customImageBase64` відновлюється лише на межі з наявним UI-кодом. Рядкові дані сцен персонажа можуть містити старі зображення у base64; схема v1 зберігає ці рядки побайтово як UTF-8, щоб не змінити непомітно ключі портретів та інвентарю. Перенесення таких значень у медіазаписи потребуватиме окремої міграції нової версії схеми.

## Медіазапис

Після основних даних ідуть `mediaEntryCount` медіазаписів. Кожен містить: `mediaId` UInt32, `nameLength` UInt16, байти безпечного відносного імені у UTF-8, `mimeLength` UInt16, байти MIME-типу у UTF-8, `dataLength` UInt32, `dataCrc32` UInt32 та байти зображення. V1 записує щонайбільше одне необов’язкове зображення предмета: ID 1, ім’я `item-image.png` або `item-image.jpg`, MIME `image/png` або `image/jpeg`. Читач відхиляє абсолютні шляхи, роздільники каталогів, `..`, повторні ID, непідтримуваний MIME-тип, неправильну сигнатуру PNG/JPEG, невірний CRC, відсутнє зображення за посиланням і зайвий медіазапис. Зовнішні шляхи до файлів у контейнері не зберігаються.

## Обмеження та інваріанти

Розмір файлу — не більше **128 MiB**; основних даних — 112 MiB; одного медіазапису — 16 MiB; кількість медіазаписів у v1 — не більше 1. Значення TLV — не більше 112 MiB, рядок — 4 MiB, глибина вкладеності — 8, персонажів — 1 000, сцен одного персонажа — 128, елементів будь-якої іншої колекції — 100 000, записів TLV загалом — 1 000 000. Кількість елементів і довжини звіряються із залишком вхідних даних до виділення пам’яті. Повторні ID персонажів, назви сцен одного персонажа та ключі в одній області неприпустимі. Обов’язкові ID й назви не можуть бути порожніми. Повне збереження може містити нуль персонажів; файл одного персонажа мусить містити його ID. Якщо колекція непорожня, ID активного персонажа має відповідати одному з її елементів. Обмеження діють і під час запису, і під час читання.

## Зафіксовані контрольні вектори

Префікс заголовка LocalData з нульовою довжиною основних даних наведено лише для перевірки розташування байтів; це не справний файл збереження:

`54 41 52 55 43 4B 50 4B 01 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00`

Значення порожньої `Collection`: `00 00 00 00`. Запис TLV з ID 2 і цим значенням: `02 00 00 00 07 04 00 00 00 00 00 00 00`. Запис TLV для `schemaVersion=1`: `01 00 00 00 02 04 00 00 00 01 00 00 00`. Тести фіксують ці байти й контрольний вектор CRC.

## Міграція та локальний запис

Основний файл локального сховища — `DndCharactersData.taruck-data`, поруч із ним використовуються `.tmp` та `.bak`. Після запису `.tmp` код відкриває його знову й перевіряє тип, CRC та відновлені дані. Лише після цього поточний основний файл переходить у `.bak`, а тимчасовий стає основним. Якщо заміна не вдалася, попередній основний файл відновлюється.

Під час першого запуску сховище пробує бінарний основний файл, потім його резервну копію. Лише коли їх немає, воно читає старий `DndCharactersData.json` або його `.bak`, нормалізує дані, записує бінарний файл і повторно читає його. Старі файли не видаляються. Якщо бінарний файл є, але ані основний, ані резервний не читається, справні старі JSON-дані можна переглянути в пам’яті лише для читання; запис блокується для захисту пошкодженого файла. Пошкоджений файл або файл новішої непідтримуваної версії ніколи не спричиняє перезапис порожніми даними. Імпорт не змінює поточні дані до перевірки файла й підтвердження користувача.
