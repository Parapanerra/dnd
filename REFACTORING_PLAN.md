# Taruck ship — актуальний план незавершених робіт

Стан повторно звірено з кодом **13 жовтня 2026 року**. Цей файл містить тільки те, що ще потрібно виправити або перевірити. Повний початковий аудит, виконання A0–A7 і хронологія рішень збережені в [REFACTORING_PLAN_HISTORY.md](REFACTORING_PLAN_HISTORY.md). Детальний аудит скриптів A7 збережено в [A7_SCRIPT_AUDIT.md](A7_SCRIPT_AUDIT.md).

Це перелік **усіх проблем, підтверджених доступними доказами на дату аудиту**, а не обіцянка, що в застосунку фізично не існує інших багів. Статичний перегляд не може показати кожен дефект реального Unity UI, Windows build, Android file picker, драйвера чи конкретного пристрою. Нову проблему додавати до Частини A лише після відтворення, логу, проваленого тесту або однозначного підтвердження в коді. Саме для пошуку таких невідомих регресій у плані залишені PlayMode-тести й повний release smoke.

## Як користуватися цим планом

- Не виконувати A0–A7 повторно: вони вже реалізовані й мають окремі статуси в `Assets/Refactoring/Baseline`.
- Перед роботою перевірити `git status` і не чіпати сторонні зміни користувача.
- Не переписувати застосунок з нуля й не міняти формат сейвів без окремої причини та міграції.
- Працювати по одному етапу з розділу «Частина A», після нього запускати відповідні тести й записувати, що фактично перевірено.
- Частина B — окремі нові функції. Вона не доводить і не замінює стабільність поточного застосунку.
- Увесь новий код одразу писати за правилами архітектури, валідації, обробки помилок і тестування з цього файла. Не завершувати задачу з навмисним дублюванням, тимчасовим глобальним станом або боргом «потім відрефакторимо», якщо це не задокументований короткий крок міграції.
- Не комітити й не пушити без прямого прохання користувача.

## Доступ до Unity для Codex

У проєкті вже підключено два засоби керування Unity:

- [Unity-плагін для Codex](https://docs.unity.com/en-us/ai/unity-plugin/codex);
- [Unity CLI з Pipeline](https://docs.unity.com/en-us/unity-cli/unity-pipeline/unity-pipeline-package).

MCP-з'єднання з Unity збережене в налаштуваннях Codex. Живе підключення вже перевірялося на відкритому редакторі: Codex прочитав сцену `cartaPersonaj` та її ієрархію. Через Unity CLI також можна звертатися до редактора, запускати доступні команди, компіляцію, тести, збірки й перевірки сцен.

Правила використання:

1. Новий чат перед сценовою, PlayMode або візуальною задачею має перевірити, чи доступний відкритий Unity Editor і живе з'єднання.
2. Якщо з'єднання доступне, використовувати Unity безпосередньо для читання ієрархії, перевірки компонентів, запуску Play Mode, тестів і збірок замість висновків лише за YAML або C#.
3. Перед зміною сцени зафіксувати її поточний стан і перевірити `git status`; не перезаписувати сторонні зміни користувача.
4. Не встановлювати іншу версію Unity: проєкт працює на вже наявній **Unity 6000.4.7f1**, якщо користувач окремо не попросить про оновлення.
5. Якщо редактор закритий або з'єднання недоступне, не видавати статичний аналіз за перевірку в Unity. Чітко записати, що саме не вдалося перевірити наживо.
6. Візуальні дефекти, зокрема тремтіння картки й поведінка оверлею, вважати виправленими лише після повторної перевірки в Play Mode у тих самих умовах. Самої компіляції для цього недостатньо.

## Структура файла та правила оновлення задач

- **Частина A** містить тільки дефекти, технічні ризики й перевірки, потрібні для стабільності вже наявного застосунку.
- **Частина B** містить тільки плани нових можливостей, яких застосунок ще не має.
- Кожна задача має один стабільний ID, один checkbox у головному чеклісті й один власний розділ. Не створювати другий опис тієї самої задачі в іншому місці файла.
- `[ ]` означає активну незавершену задачу. `[x]` означає завершення роботи над пунктом; якщо її припинено рішенням користувача до виконання критеріїв, це прямо зазначається в назві й описі, а неперевірені ризики залишаються задокументованими.
- Поки задача не завершена, її розділ містить актуальні дії та критерій готовності. Якщо план змінився, старий текст **замінюється**, а не дописується суперечливим журналом нижче.
- Коли задача завершена, у її чеклісті та заголовку ставиться `[x]`, а детальний текст «що треба зробити» видаляється й замінюється коротким підсумком за шаблоном:

```text
Стан: виконано <дата>, commit/build <ідентифікатор>.

Зроблено:
- фактичний результат;
- важливі рішення та збережена сумісність.

Перевірено:
- автоматичні тести з точним результатом;
- ручні платформи й сценарії.

Невиконане:
- немає; або конкретний залишок, через який checkbox ще не можна ставити.
```

- Не вставляти звіт про виконану задачу посеред іншого розділу й не залишати поруч одночасно старий TODO та твердження «виконано».
- Якщо під час роботи знайдено новий підтверджений дефект, створити новий пункт Частини A та одразу додати його в головний чекліст. Ідеї без підтвердженого дефекту належать до Частини B або окремого списку ідей.
- Git зберігає стару деталізацію. Головний файл повинен показувати поточний стан, а не накопичувати щоденник усіх спроб.

## Зафіксовані технічні рішення

- Поточна мета — довести до стабільного стану D&D-картку. Підтримка інших ігрових систем у цей план не входить.
- Нові збереження не використовують JSON:
  - `.tall` — усі персонажі;
  - `.tchar` — один персонаж;
  - `.titem` — один предмет;
  - `.taruck-data` — локальне сховище.
- Старі `.taruck-save`, `.taruck-character`, `.taruck-item` і JSON читаються лише для сумісного імпорту.
- Усередині файлів немає `manifest.json`, `character.json` чи іншого JSON. Локальний `.taruck-data` і `.titem` використовують сигнатуру `TARUCKPK`, явний бінарний кодек, версію та CRC32. Нові `.tall`/`.tchar` з альбомом — ZIP-контейнери з бінарними метаданими `TARUCKPK` та окремими файлами фото; старі бінарні `.tall`/`.tchar` залишаються доступними для імпорту.
- `BinaryFormatter` не використовується.
- `LegacyFieldMap_v1.csv`, старі індекси, ключі, Unity GUID і legacy fallback не видаляти, доки сумісність потрібна старим сейвам і сценам.

## Поточна оцінка архітектури й ООП

Архітектура вже придатна для подальшої підтримки: доменні моделі, бінарний кодек, репозиторії, імпорт, UI-сервіси та контролери розділені; великі компоненти здебільшого координують винесені класи; дублювання HP прибране. Новий тотальний рефакторинг «заради чистого ООП» не потрібний.

Критичні залежності від назв і неоднозначний пошук ролей закрито в A-FIX-1; загальні пошуки динамічних груп і сумісні legacy fallback збережено. Валідацію предметів закрито в A-FIX-2, а інтеграційні PlayMode-тести — в A-FIX-3. A-FIX-5 закрито рішенням користувача після часткового покращення; залишкове тремтіння спрайтів зберігається. Повний release smoke A-FIX-4 також припинено рішенням користувача; неперевірені сценарії залишаються задокументованими. Розмір класу, `static` для чистої функції, Unity `public` API або сумісний тип на кшталт `HealthBar1` самі по собі не вважаються помилкою.

### Правила архітектури для наступних змін

1. **Одна причина змін, а не ліміт рядків.** Клас ділити, коли він одночасно володіє незалежними правилами, файловим форматом, UI та навігацією. Не розбивати зв'язний view або кодек лише через кількість рядків.
2. **`MonoBehaviour` — межа Unity.** Він прив'язує компоненти, приймає Unity-події та передає роботу сервісам. Правила, валідація, перетворення й робота з даними по можливості залишаються у звичайних C#-класах.
3. **Явні залежності для критичної поведінки.** Використовувати `[SerializeField]`, `Initialize`, параметри конструктора або типізований scene-role. Глобальний пошук дозволений у composition/install-коді або для справді динамічної групи, але не як прихований спосіб знайти єдиний важливий об'єкт.
4. **Композиція переважно краща за успадкування.** Успадкування лишати для справжнього спільного контракту або сумісності Unity GUID. `HealthBar1 : HealthBar` є свідомим сумісним винятком, а не дублюванням.
5. **Без змінного глобального стану.** Нові mutable `static` singleton-и не додавати. Статичні константи, чисті функції, фабричні/Editor entry points і кодек без внутрішнього стану допустимі.
6. **Мінімальна видимість.** Поля Inspector робити `[SerializeField] private`; `public` лишати для UnityEvent, міжзбіркового API або реального зовнішнього контракту. Не звужувати метод, доки не перевірені сцени, префаби та UnityEvent.
7. **Інтерфейс лише там, де є межа.** Додавати інтерфейс для платформного провайдера, файлового сховища, джерела випадковості або кількох реалізацій. Не створювати по інтерфейсу для кожного маленького класу без потреби.
8. **Дані не залежать від UI.** Модель сейву й валідатор не повинні читати `Dropdown`, `GameObject` або сцену. UI може перевірити свої options додатково перед застосуванням уже валідної моделі.
9. **Сумісність важливіша за косметичну чистоту.** Не перейменовувати ключі, не видаляти legacy-поля, alias-класи чи fallback лише для красивішої структури без міграції та контрольного тесту старого файла.
10. **Одна відповідальність — один власник.** Не дублювати серіалізацію, валідацію, переклад, навігацію чи розрахунок у кількох контролерах; визначити основний клас-власник і викликати його.
11. **Помилка не залишає частковий стан.** Імпорт і важливі зміни виконуються через candidate/preview/commit або rollback. Повідомлення про успіх показується тільки після підтвердженого запису.
12. **Тест відповідає ризику.** Чиста логіка має EditMode-тест, зв'язування сцени — PlayMode-тест, системний файловий діалог і перенесення між платформами — ручний release smoke.
13. **Без надмірної архітектури.** Не додавати DI-контейнер, event bus, repository/interface-шар або новий framework, якщо конкретну проблему можна прозоро вирішити наявною структурою.
14. **Новий код одразу має бути робочим і підтримуваним.** Разом із функцією одразу реалізувати потрібну валідацію, повідомлення про помилки, звільнення ресурсів, збереження, локалізацію та відповідні тести. Не приймати свідомо поганий код із планом колись переписати його окремим рефакторингом.

Архітектурна зміна готова, коли її власник відповідальності зрозумілий, залежності видимі, старі дані сумісні, а відповідний рівень тестів пройдено. Сам факт застосування патерна або зменшення класу не є критерієм готовності.

У Play Mode перевірено 63 з 63 кнопок карти персонажа, зміну масштабу при наведенні/натисканні та встановлення на створену під час роботи кнопку. Перевірка у Windows/Android збірках ще потрібна.

Для шкали виснаження додано імпульс рамки кольором щойно позначеного рівня та плавну появу його позначки; на шостому рівні череп отримує один короткий контурний спалах. При знятті рівнів їхні позначки зменшуються й згасають, разом із підсвічуванням рамки. Анімація викликається з послідовності після визначення фактично змінених рівнів. У Play Mode перевірено всі шість компонентів, перехід до першого рівня при натисканні шостого, імпульс черепа на шостому та зняття рівнів 3–6 одним натисканням. Значення й збереження виснаження не змінювалися; збірки ще не перевірені.

Попередні спроби анімації `Dropdown`, які вручну змінювали розкладку створеного списку, відкочено. Нова анімація відкриває список одразу й показує пункти хвилею прозорості та кольору за 0,296 секунди. При закритті хвиля йде у зворотному порядку; тривалість закриття така сама. Координати й розміри під час анімації не змінюються. У семи числових списках сцени `cartaPersonaj` виправлено параметри самого шаблону: верхній відступ `GridLayoutGroup` 40 → 0 і зсув `Template` по Y −6,8 → 0. У Play Mode перевірено позицію першого пункту, вибір значення, зміну прозорості при закритті й скидання стану перед повторним відкриттям. Потрібна візуальна перевірка користувачем і перевірка у збірках.

- Додати реакцію на наведення кнопок у ПК-версії: тепліший відтінок і масштаб близько 1,06; при натисканні — коротке стискання до близько 0,93 із поверненням до звичайного стану. Використати наявні спрайти, без окремих зображень для кожного стану.
- На Android застосовувати лише анімацію натискання, оскільки наведення там немає.
- Для комірок магії при натисканні показувати саме **заповнення порожнього слота**: короткий спалах усередині, плавну появу позначки й легке підсвічування рамки. При знятті позначки — згасання. Не міняти напрямок або правила роботи слотів.
- Для чекбоксів ресурсів класу й раси застосувати коротку появу позначки та підсвічування в їхньому наявному стилі; при знятті — зворотний ефект.
- Для шкали втоми (рівні 1–6, від зеленого до червоного, череп на шостому) анімувати лише новопозначений рівень коротким імпульсом його власного кольору й появою позначки. На шостому рівні череп може один раз слабко засвітитися. Не затемнювати кольорові комірки й не анімувати всю шкалу.
- Плавно змінювати показане значення HP до нового числа; фактичний стан HP, збереження й правила лікування мають оновлюватися відразу, незалежно від анімації.
- Наявна смуга завантаження вже заповнюється плавно; не дублювати її анімацію без окремої потреби.
- Перевірити, що ефекти не погіршують читання тексту й не затримують натискання або зміну HP.
